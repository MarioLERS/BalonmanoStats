# HK Stats — Contexto del proyecto para Claude Code

App de estadísticas de balonmano en un único archivo `balonmano_stats.html` (~6000 líneas — actualizar esta cifra de cuando en cuando con `wc -l`, crece con cada sesión). PWA instalable, sincroniza con Firebase Firestore. Repo GitHub Pages: `mariolers.github.io/BalonmanoStats/`.

## Archivos del repositorio (todos en la raíz)
- `balonmano_stats.html` — la app entera (HTML+CSS+JS inline)
- `manifest.json` — PWA manifest. `display:standalone`, `background_color:#ffffff`, iconos `icon-192.png`/`icon-512.png` con `purpose:any` (SIN maskable — causaba fondo negro en Android, ver más abajo)
- `sw.js` — service worker, cache `hk-stats-v8` (el número sube en cada release que cambia archivos cacheados — ver `CACHE` al principio del archivo), estrategia network-first con `cache:'no-store'` y fallback a caché solo si el fetch falla de verdad
- `icon-192.png`, `icon-512.png` — PNG **opacos** (sin canal alpha, modo RGB) fondo blanco sólido
- `logo_hk.png` — logo con fondo transparente, usado en la splash screen HTML
- `INFORME_AUDITORIA_2026-09-11.html` — informe (HTML listo para imprimir a PDF) de la auditoría completa de bugs/seguridad/rendimiento hecha esa fecha; no es un archivo funcional de la app, es un entregable puntual, no hace falta mantenerlo actualizado

## Arquitectura de datos

**Almacenamiento local**: IndexedDB (`hb_store`)
- clave `hb_fs6` → `_fsCache` con `{folders:[{id,name,parentId,order}], files:[{id,name,parentId,date,data,order}]}` — directorio de partidos
- clave `hb_rivals6` → `_rivalsFSCache` con `{folders:[...], teams:[{id,name,players:[{dorsal,name}],parentId,order}]}` — directorio de equipos rivales
- clave `hb_photos` → `_photoCache` (fotos de porteras, keyed por nombre)
- clave `hb_team_photos` → `_teamPhotoCache` (fotos de equipos rivales, keyed por `team.id` — NO por nombre, porque el nombre se puede renombrar y el id nunca cambia; NO vive dentro de `_rivalsFSCache`/`hb_rivals6` a propósito, ver sección Firebase)

**Cada partido** (`file.data`) contiene: `porteros[]`, `attackers[]`, `shots[]`, `ownGoals[]`, `scoreUs`, `scoreThem`, `scoreSwapped`, `otrasContribs[]`, `timerSeconds`.

**Cada shot** (ver `registerShot()`) tiene: `id` (`Date.now()`), `time` (formato `MM:SS`, reloj de partido), `videoSeconds` (reloj de vídeo real, para exportar a XPS sin calibrar), `zone`, `result` (`'parada'|'gol'|'fuera'` — `'sinportero'` es un valor LEGADO que ya no genera ningún flujo actual, ver más abajo), `goalPos` (9 zonas a puerta `'Alto/Medio/Bajo izq/centro/der'`, o 9 zonas nuevas de "fuera" — `'Fuera alto/medio/bajo izq/der'` junto a los palos y `'Fuera arriba izq/centro/der'` sobre el larguero — para tiros que van fuera, ver regla 22), `porteroId`/`porteroName` (`porteroId:null` si `noGk`), `attackerId`/`attacker`, `pf`/`pd` (bool, punto fuerte/débil del atacante), `hab` (bool, con habilidad), `traj` (`'cruzado'|'paralelo'|undefined`), `noGk` (bool, portería vacía — el equivalente actual a lo que antes era `result:'sinportero'`).

**ownGoals**: `[{time, id}]` — goles propios, registrados automáticamente al pulsar +1 en el marcador de nuestro equipo (función `changeScore('us', +1)`).

## Firebase Firestore
Proyecto `balonmanostats-a0fa1`, colección `sync`. Documentos:
- `hb_structure` — `{folders, fileIds[], ts}` (metadata ligera de qué partidos existen)
- `hb_file_<id>` — un documento por partido (datos completos, sin fotos — se limpian antes de subir)
- `hb_rivals6` — el directorio de rivales completo
- `hb_photo_<kind>_<key>` — un documento POR FOTO (2026-09-15, ver regla 21): `kind` es `'portero'`, `'equipo'` o `'temporada'`, `key` es el nombre normalizado (porteras) o el id (equipos/temporada). Nunca un blob único con todas las fotos juntas.

**Sync incremental — reescrita el 2026-09-11 para eliminar dos carreras de sobrescritura reales (ver regla 15)**:
- `_fbSync(key, value)` es quien de verdad sube `hb_structure`. `saveFS()` la llama siempre. Desde el fix, **ya NO sobrescribe** `hb_structure` a ciegas con lo que sabe este dispositivo: hace `_fbPull('hb_structure', ...)` primero y fusiona por id (unión de `folders`/`fileIds` locales + remotos) antes de escribir. Un dispositivo que añade un partido no puede pisar la referencia al partido que otro dispositivo acababa de añadir.
- `saveMatch()` (botón manual "💾 Guardar partido") → `saveFS(fsData)` (sube la estructura fusionada vía `_fbSync`) + `syncSingleMatchToCloud(entry)` (sube solo el documento de ESTE partido, `hb_file_<id>` — ya NO recalcula ni sube su propia copia de `hb_structure`, era una segunda subida redundante con la misma carrera que `_fbSync` ya resuelve).
- `_fbMergeOnStart()` (al arrancar, y también en el listener de tiempo real): si la nube tiene un timestamp más reciente, YA NO reemplaza `_fsCache` entero — fusiona por id (misma política que `importData`: añade lo que falta, se queda con la versión más reciente por fecha si el partido existe en ambos lados). Antes podía borrar en silencio un partido local aún no subido.
- El listener de tiempo real (`_startFbSync`, cerca del arranque) escucha el documento `hb_structure` (antes escuchaba `hb_fs6`, que ningún write genera — nunca se disparaba) y, al recibir un cambio, llama a `_fbMergeOnStart()` en vez de parsear a mano.
- `saveFS(fs)` internamente separa la parte local (`_persistLocalOnly(fs)`: solo `_fsCache`+IndexedDB, sin red) de la sincronización a la nube (`_fbSync`). `_persistLocalOnly` es lo que reutiliza `autosaveMatchLocal()` (ver regla 16) para no disparar red en cada evento del partido.
- **Rivales (`hb_rivals6`) tienen ahora el MISMO tratamiento que partidos (2026-09-15, ver regla 23)**: `_fbSyncRivals(rfs)` (pull→merge→write, igual que `_fbSync`) y `_fbMergeRivalsOnStart()` (igual que `_fbMergeOnStart`, con su propio listener en tiempo real). Antes `syncRivalsIncremental()` subía `_rivalsFSCache` tal cual con un `_fbSetDoc` directo, sin mirar la nube antes — esa asimetría con partidos fue la causa real de perder el directorio de rivales entero el 2026-09-15 (un dispositivo con rivales vacíos hizo una edición mínima y pisó la nube con la nada). `syncRivalsIncremental()` YA NO EXISTE, sustituida por `_fbSyncRivals`.
- **`syncAllToCloud()`/`downloadAllFromCloud()` (los botones ☁️/⬇️) YA NO EXISTEN** — eran sobrescritura total en cada sentido, sin fusión, y son la causa directa del incidente de pérdida de datos del 2026-09-15 (ver regla 23). Sustituidos por un único botón **`syncNow()`** ("🔄 Sincronizar ahora", dentro del directorio de partidos, ya no en el header), que reutiliza `_fbSync`/`_fbMergeOnStart`/`_fbSyncRivals`/`_fbMergeRivalsOnStart` (nunca sobrescribe) y además re-sube el contenido de cada partido local como red de seguridad (por si alguna subida automática anterior falló en silencio).
- **Limitación conocida y aceptada de la fusión por unión de ids**: no hay registro de borrados reales propagado a la nube, así que en el peor caso puede quedar un id "fantasma" en `fileIds` sin partido real detrás (inofensivo: no resucita datos borrados, ese `hb_file_<id>` ya no existe una vez pasan los 30 días de papelera). Arreglarlo del todo pediría tombstones, cambio de diseño mayor no hecho.
- `_fbSetDoc`/`_fbGetDoc`/`_fbDoc` cuelgan de `window` (definidos en un `<script type="module">` de Firebase al principio del `<head>` del documento principal — desde el 2026-09-15 ese mismo texto se copia también, vía `FIREBASE_INIT_SRC`, al `<head>` que genera `buildSeasonHTML` para la ventana de temporada, ver regla 21).

## Reglas críticas (aprendidas a base de romper la app)

1. **HAY DOS FUNCIONES QUE DIBUJAN LA MISMA TABLA "Por zona de campo" en el resumen de temporada**: `sGroupRow` (en el script principal, genera el HTML inicial) y `buildZoneRows` (duplicada y MINIFICADA dentro del string gigante que construye la página de temporada — se ejecuta cada vez que se aplica un filtro dentro de esa ventana). Si tocas la tabla de zonas, **hay que editar las dos**, o corres el riesgo de que se vea bien al abrir pero mal al filtrar (esto costó una sesión entera de debugging).

2. **El HTML de la ventana de temporada es un string JS gigante** construido con concatenación `+'...'`. Vive dentro de `function buildSeasonHTML(folderName, files, folderId)`. Para editar código JS que vive DENTRO de ese string (ej. `buildZoneRows`), hay que respetar el escapado de comillas (`\\'` dentro de comillas simples exteriores). Verificar sintaxis extrayendo el fragmento y evaluándolo con Node antes de dar por bueno un cambio.

3. **Radar de zonas de campo** (`drawRadar` en el script principal, canvas `#radar-canvas`): usa un **overlay SVG transparente** (`#radar-zone-overlay`) posicionado encima del canvas con el MISMO `viewBox` que las dimensiones físicas del canvas (`W x H`, ej. 600x530) para que los círculos clicables coincidan exactamente con los dibujados. NO usar `canvas.offsetWidth` para mapear clicks (puede ser 0 antes del layout, o desajustarse con `devicePixelRatio`) — usar el espacio de coordenadas del propio canvas y dejar que el SVG escale solo vía CSS `width:100%`.

4. **Tamaño de los círculos del radar**: escala fija 1-10 por tipo (gol/parada/pct), NO depende de ningún total (ni `totalLanz` ni `maxZoneLanz`) para que el tamaño no cambie al aplicar filtros. Cada círculo (gol/parada/pct) tiene su radio independiente. Orden de dibujo: el círculo más grande siempre al fondo (`.sort(function(a,b){return b.r-a.r;})`), transparencia ~55-60% para que se note la superposición.

5. **Timeline / gráfico de evolución** (`drawTimeline`, canvas `#timeline-canvas`): usa tiempos EXACTOS fraccionarios (`timeToSec(s.time)/60`), no agrupa por minuto. Un punto por evento (diagonal), no función escalón (quedaba "cuadrado", se revirtió a petición del usuario). Al hacer click, busca el evento (shot u own goal) más cercano en tiempo y muestra un `alert()` con: minuto, marcador reconstruido en ese instante (recorriendo `shots`+`ownGoals` cronológicamente, NO usando el marcador final), y detalles del lanzamiento.

6. **`_idbGetSync` NO EXISTE** — es una función que se intentó usar por error en el pasado. Usar siempre los cachés síncronos ya cargados al arrancar: `_fsCache` y `_rivalsFSCache`.

7. **El modal HTML del directorio de rivales debe estar en el `<body>`, FUERA de cualquier `<script>` y fuera del div `.app`**, justo antes de `</body>`. Meterlo sin querer dentro de un bloque `<script>` (aunque sea en medio de un string) rompe TODO el JS de la página con `SyntaxError: Invalid or unexpected token` — pasó varias veces al editar con `str_replace` de forma descuidada.

8. **PWA / iconos**: los iconos DEBEN ser PNG 100% opacos (sin canal alpha, `Image.new('RGB', ...)` en PIL, no `RGBA`). Un icono con `purpose:"maskable"` y fondo transparente hace que Android rellene la transparencia con NEGRO al recortar la máscara adaptativa — causó semanas de "pantalla de carga negra" en tablets Android. Manifest actual usa solo `purpose:"any"` en ambos tamaños, sin maskable. NUNCA sobrescribir el manifest con un blob URL generado por JS (`URL.createObjectURL`) — rompe la resolución de rutas relativas de los iconos y Chrome deja de ofrecer "Instalar app" (solo ofrece "Acceso directo").

9. **Splash screen HTML** (`#splash-screen`, antes de `.app`): tiempo mínimo garantizado de 2.2s visible (usa `Date.now()` al inicio + `setTimeout` calculado con el tiempo restante), independientemente de cuándo `window._appLoaded` se ponga a `true`. Si no, se oculta casi instantáneamente y no da tiempo a leer "HK STATS".

10. **Botones HAB / Cruzado / Paralelo** en el registro de lanzamiento: apilados verticalmente (`flex-direction:column`) en un div de 36px de ancho junto al SVG de portería, cada botón de 30px de alto. `selectedTraj` (`'cruzado'|'paralelo'|null`) se guarda en `shot.traj` al registrar y se resetea después.

11. **Filtros de estadísticas** — variables globales: `filterPortero`, `filterPlayer`, `selectedPfPd`, `statsZoneFilter`, `statsTrajFilter`, `statsGoalPosFilter`. Todos se aplican en `getFilteredShots()`. Cambiar cualquiera debe llamar a `renderStats()` Y `drawTimeline(getFilteredShots())` para que el timeline también refleje el filtro (marcadores sobre las líneas de gol/parada en su posición Y real, no en el eje X).

12. **Deduplicación al construir el resumen de temporada** (`openSeasonSummary`): recorrido de carpetas con `seenIds{}` (por `file.id`) y `visitedFolders{}` para evitar contar el mismo partido dos veces si la estructura de carpetas tuviera alguna referencia duplicada.

13. **Para pasar funciones al scope de la ventana de temporada sin duplicar código (retipeado a mano)**: usar reflexión con `.toString()`, no reescribir la función dentro del string. Patrón usado por `XG_MODEL_SRC` (ver sección del modelo xG más abajo): se define la función UNA vez en el script principal, y justo después se construye `var XG_MODEL_SRC = [fn1, fn2, ...].map(function(f){return f.toString();}).join('\n') + 'var CONST=...;'` con `JSON.stringify` para las constantes. Ese string se inyecta con `+XG_MODEL_SRC+` (sin comillas, es una referencia a variable, no un literal) en el punto de `buildSeasonHTML` donde se define `ALL_SHOTS`/`ALL_MATCHES`. Al ser literalmente el mismo texto que corre en el script principal, es imposible que diverja — evita el problema real de `sGroupRow`/`buildZoneRows` (regla 1). **Cuidado con dejar un `+` de más o de menos alrededor de la inserción**: `+XG_MODEL_SRC+` seguido de otra línea que ya empieza por `+'...'` duplica el operador y el string siguiente se evalúa como `+'texto'` (un unario, no una concatenación) — el resultado es que ese fragmento se convierte silenciosamente en la cadena `"NaN"` en vez de aparecer como texto. Si algo del script de la ventana de temporada desaparece o aparece como "NaN" sin que salte ningún error de sintaxis, sospechar primero de un `+` de más/menos cerca de la última zona tocada.

14. **Para funciones que van DENTRO del string de `buildSeasonHTML` y tienen muchas comillas anidadas** (p.ej. `drawSeasonGoal`, que genera SVG con atributos entre comillas dobles y JS con comillas simples): se codifican en base64 y se reconstruyen con `eval(decodeURIComponent(escape(atob(_dsgB))))`. Esto NO es ofuscación deliberada, es para evitar el infierno de escapado de comillas en una función ya anidada dentro de otro string. Al editar esa función: decodificar con Node (`Buffer.from(b64,'base64').toString('binary')` + `decodeURIComponent(escape(...))`), editar el JS plano, re-codificar con `Buffer.from(textoNuevo,'utf8').toString('base64')`, y verificar el round-trip antes de sustituir el literal `_dsgB="..."` en el archivo.

15. **Autoguardado local del partido en vivo** (`autosaveMatchLocal()`, 2026-09-14): nació de un caso real — con conexión inestable en tablet, la app se recargaba (el SW cae a caché al fallar el fetch) y como nada se guardaba hasta el primer "💾 Guardar partido" manual, se perdía el partido entero. `autosaveMatchLocal()` persiste en IndexedDB (vía `_persistLocalOnly`, sin tocar Firebase) y se llama tras **cada acción que mute el partido en curso**: `registerShot`, `deleteShot`, `changeScore` (goles propios), y los tres puntos de "otras contribuciones" (añadir, restar, `deleteOtra`). También se llama una vez en `createNewMatch()` justo después de `resetAppState()`, para que `currentMatchId` quede fijado desde el primer segundo — antes se quedaba en `null` hasta el primer guardado manual, y con él a `null` los seguros ya existentes (`beforeunload`/`visibilitychange` en `_saveEditedShot`, etc., todos gateados por `if(currentMatchId)`) no hacían nada. **Regla para el futuro**: cualquier función nueva que añada/edite/borre un evento del partido (un tiro, un gol, una contribución, o lo que sea que se añada más adelante) tiene que terminar llamando a `autosaveMatchLocal()`, igual que ya hacen estas. A propósito NO sincroniza con la nube en cada llamada (eso sigue siendo cosa de `saveMatch()`, el botón manual, que se mantiene intacto y no se ha tocado su comportamiento) para no disparar tráfico de red en cada tiro — si se añade un nuevo punto de mutación y se le olvida esta llamada, vuelve el mismo bug de origen.

16. **Elementos que se recrean en cada render necesitan limpieza EXPLÍCITA de listeners, no un flag `_algoAttached`** (encontrado en `attachDrag`, la fuga de memoria del arrastre de foto de portero — auditoría 2026-09-11). Si una función tipo `renderX()` hace `el.innerHTML=''` y reconstruye el DOM en cada llamada, un guard `if(elemento._xAttached) return;` puesto dentro de `attachY(pid)` NUNCA sirve para deduplicar, porque el elemento siempre es nuevo — cada llamada añade listeners de `document` (`mousemove`/`mouseup` etc.) que nunca se eliminan y se acumulan sin límite. La solución es un registro de funciones de limpieza por id (`var _xCleanupByPid = {}`), invocar la del id anterior antes de enganchar los nuevos listeners, y guardar la nueva al final. Antes de copiar un patrón de "guard con flag en el elemento" de un sitio del código a otro, comprobar primero si el elemento al que se aplica se recrea en cada render o es fijo (como `attachStatsDrag`, donde el flag SÍ funciona porque el elemento nunca se recrea).

17. **`resetAppState()` (nuevo partido) y `loadMatchData()` (abrir partido existente) tienen que resetear la MISMA lista de variables de selección de tiro** (`selectedZone`, `selectedGoalPos`, `selectedResult`, `selectedNoGk`, `selectedHab`, `selectedTraj`, `selectedPfPd`) y repintar los mismos botones (`[data-zone]`, `.gcell`, `.btn-result`, `zone-active-lbl`, `goal-active-lbl`) antes de terminar, más una llamada a `checkReady()`. Si una selección a medias del partido A queda sin resetear, se cuela en el partido B al abrirlo desde el explorador (bug real, corregido en la auditoría 2026-09-11). Si se añade un campo nuevo de selección de tiro en el futuro, hay que añadirlo a los dos sitios.

18. **Todo dato que pueda venir de fuera (nombre de rival, de portera, de atacante — por entrada libre, import de `.json`, import XPS, o sync desde otro dispositivo) tiene que pasar por `escHtml()` antes de insertarse en el DOM vía `innerHTML`**, y por `JSON.stringify(...)` (nunca comillas puestas a mano) si se interpola dentro de un literal de string JS. `buildSeasonHTML` fue la única función del archivo que se saltaba esto (auditoría 2026-09-11, hallazgo de XSS más grave de toda la revisión) — un nombre con `"` rompía directamente un `var FOLDER_ID="..."` sin pasar siquiera por el parser de HTML. `safeJSON()` (usada para `ALL_SHOTS`/`ALL_MATCHES`/etc. en la ventana de temporada) también tuvo que endurecerse con un `.replace(/<\/script/gi,'<\\/script')`, porque solo escapar los caracteres no-ASCII (código >= 128) no protege contra que un dato externo contenga literalmente `</script>` y corte el bloque a mitad.

19. **Antes de borrar cualquier función por parecer "no usada", confirmar CERO referencias** (grep del nombre exacto en todo el archivo, y de cualquier id de botón que la función busque por `getElementById`) **y avisar explícitamente al usuario antes de tocarla**, aunque esté clarísimo que no se usa. Así se detectaron y eliminaron `syncRivalsToCloud()`/`downloadRivalsFromCloud()` (auditoría 2026-09-11) — nunca se borra nada "porque sobra", solo tras confirmar y con permiso.

20. **CSS de impresión (`@media print`)**: hay DOS copias — una para el partido en vivo (bloque `<style>` normal, cerca de la línea 255) y otra para el resumen de temporada (dentro del string de `buildSeasonHTML`, sin comillas anidadas raras así que se edita directo, sin el truco base64 de la regla 14). Ambas usan `@page{size:auto;margin:6mm}` (antes 10mm/12mm en el partido, y SIN regla `@page` en temporada — heredaba el margen grande por defecto del navegador) y `break-inside:avoid`+`page-break-inside:avoid` en el contenedor de cada tarjeta (`.stat-block` en partido, `.card` en temporada) para que no se corte una tarjeta a mitad de página. Si una tarjeta es más alta que una página entera, el navegador rompe igual — es la única situación en la que `avoid` no se puede respetar, no es un fallo del CSS.

21. **Sincronización de fotos entre dispositivos** (`_photoDocId`/`_uploadPhoto`/`_downloadPhotoIfMissing`/`_deletePhoto`, 2026-09-15): un documento de Firestore POR FOTO (`sync/hb_photo_<kind>_<key>`), nunca un blob con todas juntas — así ningún documento se acerca al límite de 1MB de Firestore por muchas porteras/equipos que se acumulen. `_uploadPhoto` no sube si la foto en base64 pesa ≥900KB (deja margen bajo el límite de 1MB) — se queda solo en local en ese caso, sin romper nada. La descarga es SIEMPRE perezosa (`_downloadPhotoIfMissing`): un dispositivo solo pide la foto que le falta justo cuando la necesita mostrar, nunca "todas las que existen" — así se cumple lo que pidió el usuario ("sin que se acumule o genere un problema para la memoria"). Al borrar el elemento dueño de la foto (ej. un equipo del directorio de rivales), se llama a `_deletePhoto` para no dejar documentos huérfanos en la nube para siempre. Aplicado a tres cosas:
    - **Porteras** (`savePorteroPhoto`/`rehydratePhotos`, ya existían — solo se les añadió la subida/descarga): keyed por nombre normalizado.
    - **Equipos rivales** (`saveTeamPhoto`/`getTeamPhoto`/`ensureTeamPhoto`, funcionalidad NUEVA — antes `team` no tenía ningún campo de foto): keyed por `team.id`. UI: un círculo de 44px en cada tarjeta del directorio de rivales (`renderRivalsDir`), clic para elegir imagen vía `#rival-photo-input` (input de archivo oculto, un solo input reutilizado para todos los equipos vía `rivalPhotoTarget`). La foto NO se guarda dentro de `hb_rivals6`/`_rivalsFSCache` (evitaría que cada pequeño cambio del directorio — renombrar una carpeta, mover un equipo — re-subiera todas las fotos como parte de ese documento); vive en su propio store `hb_team_photos`/`_teamPhotoCache`, igual que las fotos de portera.
    - **Logo de temporada** (dentro de `buildSeasonHTML`, el caso más difícil): la ventana/iframe de temporada es un documento COMPLETAMENTE APARTE, sin el `<script type="module">` de Firebase del documento principal — hasta ahora tenía CERO acceso a la nube (el logo solo vivía en `localStorage.hb_season_cfg_<FOLDER_ID>` de ESE dispositivo). Solución: se captura el texto real de ese `<script type="module">` en tiempo de ejecución (`var FIREBASE_INIT_SRC = document.querySelector('script[type="module"]').textContent`, definida junto a `PHOTO_SYNC_SRC`) y se inyecta tal cual, envuelto en su propio `<script type="module">`, en el `<head>` que genera `buildSeasonHTML` (justo antes de `</head>`) — la ventana de temporada monta así su PROPIA instancia de Firebase, independiente de la del documento principal pero con la misma config, sin duplicar el código a mano (mismo principio que la regla 13, pero para un `<script type="module">` en vez de una función). `PHOTO_SYNC_SRC` (reflexión `.toString()` de las 4 funciones genéricas) se inyecta junto a `XG_MODEL_SRC` en el mismo punto de siempre. El input `#season-logo-input` sube la foto (`_uploadPhoto('temporada', FOLDER_ID, ...)`) justo después de guardarla en `localStorage`; el `window.onload` de esa ventana intenta descargarla (`_downloadPhotoIfMissing('temporada', FOLDER_ID, ...)`) solo si no hay ninguna guardada localmente para esa carpeta.

22. **9 zonas "Fuera" en el SVG de registro de lanzamiento** (`#goal-svg`, 2026-09-15): antes, un tiro que iba fuera (`result:'fuera'`) obligaba a elegir igualmente una de las 9 celdas DENTRO de la portería para `goalPos` — dato falso (esa portera nunca tuvo esa opción real de parada ahí) que además se veía en el popup de detalle del tiro como si tuviera un xGOT calculado. 28. **Segundo incidente, el mismo día: `syncNow()` "terminaba bien" pero dejaba la biblioteca local vacía (2026-09-15, encontrado y arreglado horas después de la regla 23)**: tras el primer incidente, la nube quedó perfectamente reconstruida (68 partidos, 15 rivales, verificado leyendo Firestore directamente), pero un dispositivo que pulsaba "🔄 Sincronizar ahora" veía "✅ Sincronización completa" y seguía sin ver ni un solo partido. Causa raíz, **dos bugs distintos apilados**:
    - **(a) Carrera de timestamps dentro de `syncNow()`**: llamaba a `_fbSync('hb_fs6', fs)` y a `_fbMergeOnStart()` uno detrás de otro SIN esperar a que el primero terminase. `_fbSync` escribe `hb_fs6_ts` local en el MISMO instante en que escribe en la nube (antes de que su propia escritura remota haya siquiera terminado); si `_fbMergeOnStart` leía ese `hb_fs6_ts` recién puesto ANTES de haber bajado nada, la comparación `remoteTs > localTs` salía falsa (ts casi idénticos) y el pull+merge de los partidos individuales nunca llegaba a ejecutarse — el dispositivo se quedaba exactamente igual que antes de pulsar el botón, sin ningún error visible. **Fix**: `_fbSync`, `_fbMergeOnStart`, `_fbSyncRivals` y `_fbMergeRivalsOnStart` ahora aceptan un `done` callback opcional (no rompe ninguna llamada existente que no lo pase) y `syncNow()` secuencia de verdad: primero `_fbMergeOnStart(cb)` → dentro `_fbMergeRivalsOnStart(cb2)` → SOLO cuando los dos han terminado de verdad, entonces sube el contenido de cada partido y fusiona la estructura de vuelta. Nunca más "a la vez sin esperar".
    - **(b) Marca de tiempo local que puede quedar permanentemente "adelantada" sin haber traído nada**: si un intento anterior de sincronizar sufrió el bug (a) (o cualquier otra causa dejase `hb_fs6_ts`/`hb_rivals6_ts` locales apuntando a un valor alto sin que `_fsCache`/`_rivalsFSCache` reflejaran contenido real), CUALQUIER merge automático futuro (incluido un simple reinicio de la app) seguiría comparando `remoteTs > localTs` y saliendo falso para siempre — el dispositivo queda convencido de que "ya está al día" sin estarlo, sin ningún mecanismo de auto-corrección. **Fix**: `_fbMergeOnStart(done, force)` y `_fbMergeRivalsOnStart(done, force)` aceptan un segundo parámetro `force` que se salta la comparación de timestamps y fuerza el pull+merge completo siempre; `syncNow()` SIEMPRE llama con `force=true` (un "Sincronizar ahora" manual no se debe fiar nunca de una marca que podría estar corrupta — es justo su razón de ser). El merge automático pasivo de arranque/tiempo real (`_startFbSync`) sigue llamando SIN `force` (comportamiento normal, eficiente, sin re-descargar todo en cada evento).
    - **Verificación**: se reprodujo el bug (a) con una simulación que imita exactamente la secuencia real (latencia de red variable, `hb_file_*` más lentos que `hb_structure`) contra un `_fsCache` local vacío — confirmado que se quedaba en 0 archivos. Se reprodujo también el bug (b) con una marca de tiempo local deliberadamente corrupta y se confirmó que un merge SIN `force` no repuebla nada, mientras que `syncNow()` (con `force`) sí lo consigue. Ambos casos verificados también arreglados tras el fix, con datos sintéticos Y con los datos reales de la nube (68 partidos/15 rivales) leídos directamente de Firestore en el momento de arreglar esto.
    - **Lección para el futuro**: cualquier función de sincronización que se llame más de una vez seguida (como hace `syncNow()`) tiene que encadenarse de verdad con callbacks/promesas — nunca lanzar dos operaciones de sync "en paralelo sin esperar" cuando una de ellas escribe una marca de tiempo que la otra usa para decidir si tiene trabajo que hacer.

36. **"Sincronizar ahora" tardaba varios minutos, y volvía a tardar igual al repetirlo (2026-09-18)**: diagnosticado leyendo directamente la colección `sync` de Firestore en producción (67 partidos reales, ~6.75MB en total). Dos causas independientes, ambas confirmadas con datos reales antes de tocar nada:
    - **Causa 1 — cada sincronización transfería TODO el histórico, no solo lo nuevo**: tanto el arranque automático como "Sincronizar ahora" (`_fbMergeOnStart`) volvían a descargar el contenido COMPLETO de los 67 partidos en cada ejecución, sin comprobar si ya se tenían — y "Sincronizar ahora" además volvía a SUBIR el contenido completo de los 67 partidos locales cada vez (`_step2` dentro de `syncNow()`), aunque no hubiera cambiado nada desde el intento anterior. Por eso repetirlo tardaba exactamente igual.

Marca "confirmado sincronizado" un partido cuando se sube con éxito (`syncSingleMatchToCloud`, subida individual de `saveMatch()`, y la subida completa de `_step2`) o cuando se baja con éxito (`_fbMergeOnStart`). La subida completa se salta cualquier partido ya confirmado, dejando solo la red de seguridad para los que de verdad nunca se subieron. `syncSingleMatchToCloud()` ahora también re-sube la estructura (documento pequeño) justo después de confirmar su propio partido, para que el `ts` nuevo llegue a `hb_structure.fileTs` y otros dispositivos sepan que hay algo que bajar (antes `saveFS()` subía la estructura ANTES de conocer ese `ts`, dejando la marca compartida desactualizada).

37. **BUG GRAVE introducido por la regla 36 (mismo día, 2026-09-18): "no termina nunca de sincronizar"** — el usuario reportó justo después de desplegar la regla 36 que la sincronización se quedaba colgada indefinidamente (no solo lenta: no terminaba nunca). Causa raíz encontrada reproduciendo el problema en una simulación real de Node (con un Firestore falso que imita el "eco local" de escrituras propias, como hace Firestore de verdad): la rama `else` de `_fbMergeOnStart()`/`_fbMergeRivalsOnStart()` (cuando decide "la nube no tiene nada más nuevo que lo mío") volvía a subir la estructura "por si acaso" (`_fbSync`/`_fbSyncRivals`). 39. **Reloj de vídeo real perdía tiempo al bloquear la pantalla de la tablet (2026-09-20)**: reportado por el usuario durante el registro de un partido real ("esto hará que se descuadren los tiempos de los cortes"). Causa: `realSeconds` se incrementaba con `realSeconds++` en cada "tic" de un `setInterval` — pero un móvil/tablet **suspende por completo** los `setInterval` de una pestaña/PWA en segundo plano cuando se bloquea la pantalla (ahorro de batería del sistema operativo, no hay forma de evitarlo desde una PWA), así que cada segundo con la pantalla bloqueada se perdía para siempre y el reloj se quedaba clavado exactamente donde estaba al bloquear.

Así, aunque el intervalo no se haya ejecutado NI UNA SOLA VEZ durante todo el bloqueo, en cuanto la app vuelve a ejecutarse (se desbloquea la tablet) el valor salta de golpe al tiempo real transcurrido, sin arrastrar ningún desfase. Se sustituyeron todas las lecturas de `realSeconds` que capturan un instante concreto (el segundo de vídeo guardado en cada tiro, en cada "otra contribución", y al guardar el partido) por `_syncRealSeconds()`, para que ese valor puntual también esté siempre al día y no dependa de cuándo tocó el último tic. `stopTimer()` (Detener) sincroniza una última vez antes de congelar el contador; `startTimer()` (Iniciar) reconstruye `realStartTs` a partir de lo ya contado, para poder pausar y reanudar sin perder ni duplicar tiempo.
    - **Verificación**: test de Node con un reloj de sistema simulado que salta 120 segundos SIN invocar el temporizador ninguna vez (justo lo que pasa de verdad con la pantalla bloqueada), confirmando que el contador salta directamente al tiempo real transcurrido al reanudar en vez de quedarse atrás; y un segundo test que confirma que Detener y volver a Iniciar más tarde conserva el tiempo ya contado sin perderlo ni duplicarlo. ## Modelo xG / xGOT / GSAx (portero)
Implementado en el script principal (bloque `// ===== MODELO xG / xGOT / GSAx (portero) =====`, justo después de las variables globales de porteros/shots). Adaptado de la especificación de Handball Stats Pro (aportada por el usuario el 2026-09-11) a los campos que existen en esta app.

**Mapeo de `zone` (mezcla tipo+posición de pista en esta app) a tipo del modelo** — decisión confirmada con el usuario:
- `Extremo izq/der` → Wing
- `6m izq/cent/der` → **Break** (penetración, NO Pivot — esta app no tiene zona propia de pivote)
- `Lateral izq/der`, `Central` → Long (9m)
- `7 metros` → 7M, `Contraataque` → Counter (estos dos sin modificador de lado: son valores únicos de `zone`, no tienen variante izq/centro/der)

**`goalPos` coincide 1:1 con la malla 3x3 del modelo** (`Alto/Medio/Bajo` × `izq/centro(centro)/der`) — no hace falta remapeo.

**Funciones**: `calcularXG(shot, opts)`, `esTiroAPuerta(shot)`, `calcularXGOT(goalPos)`, `calcularGSAx(shotsArr, porteroId)`, `gsaxPorZona(shotsArr, porteroId)`, `gkScore(savePct, gsax, porZona, minMuestra)`, `xgTotalEquipo(shotsArr, opts)`. Todas puras, nunca inventan un valor que falte: si `zone` no está en el mapa o `goalPos` no está, devuelven `null` y ese lanzamiento queda excluido del cálculo correspondiente (no se cuenta como 0). (`xgBalanceZona` existió brevemente pero se eliminó — ver más abajo.)

**Columnas "Balance" y "GSAx" en las tablas "Por zona de campo"** (decisión final del usuario, 2026-09-11 — se descartó una versión anterior basada en `calcularXG`/zona de pista, la función `xgBalanceZona` ya no existe): ambas salen de la MISMA llamada a `calcularGSAx(gruposDeEseZonaDePista, null)`, agrupando por zona de PISTA pero mirando el `goalPos` (zona de portería) de esos tiros:
- **Balance**: `g.gsax` — paradas esperadas (según xGOT/goalPos) frente a las paradas reales. Positivo = paró más de lo esperado.
- **GSAx** (a la derecha de Balance): las paradas esperadas totales en bruto, sin restarle nada — `g.tirosConDato - g.xGOTRecibido`.
Ambas aparecen juntas en las tres implementaciones que hay que mantener sincronizadas (`addGroupRow` en vivo, `sGroupRow` estática de temporada, `buildZoneRows` minificada dentro de la ventana hija).

**El xGOT en bruto (0-1 o %) NO se muestra en los heatmaps de portería** (`drawGoalHeatmap`/`drawSeasonGoal`) — esos solo llevan el GSAx por zona de portería. El xGOT recibido (agregado) se ve únicamente como cifra en el panel "Global" de las estadísticas de cada partido (`g-xgot`, calculado como `calcularGSAx(fs,null).xGOTRecibido`).

**Dónde se usa**:
- Partido en vivo: panel "Global" (xG rival, **xGOT recibido**, GSAx equipo), tarjeta de cada portero (GSAx **y `🔥 Racha`**, ver más abajo — desde 2026-09-14 el ⭐ valoración/`gkScore` YA NO aparece aquí, se sustituyó por la racha), heatmap de portería (`drawGoalHeatmap`, solo GSAx por zona, sin xGOT), tabla "Por zona de campo" (`addGroupRow`: columnas Balance y GSAx), log de lanzamientos y popup del timeline (xG/xGOT del tiro individual — aquí sí se ve el xGOT puntual de ESE tiro, es distinto del agregado del panel Global).
- Resumen de temporada: tarjetas `.pcard` (GSAx y **⭐ valoración/`gkScore` — esta sí la sigue mostrando, no se tocó**, vía `allShots` en scope normal), línea de resumen bajo "Efectividad global por portera" (xG/GSAx del equipo), heatmap de portería de temporada (`drawSeasonGoal`, solo GSAx, sin xGOT — usa `XG_MODEL_SRC`, ver regla 13), tabla "Por zona de campo" acumulada en sus DOS versiones (`sGroupRow` estática y `buildZoneRows` minificada dentro de la ventana hija — ambas con columnas Balance y GSAx, hay que mantenerlas sincronizadas).

**`rachaPortero(shotsArr)`** (2026-09-14, función independiente del modelo xG, no usa ninguna de sus constantes): cuenta las paradas o goles consecutivos de un portero, ordenando por `timeToSec(s.time)` (no por el orden de registro, para que editar un tiro no descuadre la racha). Los tiros `fuera` y `noGk` se ignoran (no cuentan ni cortan la racha). Devuelve `{count, tipo:'gol'|'parada'}` o `null` si no hay tiros. En la tarjeta de portero del partido en vivo se muestra como `🔥 count`, en rojo si `tipo==='gol'` (racha de goles encajados) y en verde si `tipo==='parada'`.

## Verificación de sintaxis (flujo de trabajo usado hasta ahora)
El HTML tiene 3-4 bloques `<script>`: uno `type="module"` de Firebase, uno pequeño de splash screen, y el principal (gigante, ~4000 líneas) con toda la lógica de la app. Antes de dar por bueno un cambio:
```python
import re, subprocess
with open('balonmano_stats.html') as f: c = f.read()
scripts = list(re.finditer(r'<script(?:\s[^>]*)?>(.+?)</script>', c, re.DOTALL))
with open('/tmp/main.js', 'w') as f: f.write(scripts[2].group(1))  # el índice del script principal puede variar
r = subprocess.run(['node', '--check', '/tmp/main.js'], capture_output=True, text=True)
print('OK' if r.returncode == 0 else r.stderr)
```
Para el código JS que vive DENTRO del string de `buildSeasonHTML` (la ventana de temporada), hay que además evaluar la concatenación de strings con Node para extraer el JS real antes de poder chequear su sintaxis (ver regla 2).

## Cómo pedir cambios
Este proyecto se ha desarrollado íntegramente a base de `str_replace` en el archivo. Al pedir un cambio, conviene:
1. Leer primero el fragmento relevante con `view` antes de tocar nada (el archivo es grande y hay funciones con nombres parecidos o duplicadas, ver regla 1)
2. Verificar sintaxis con Node antes de dar el cambio por bueno
3. Si el cambio afecta a la ventana de temporada, comprobar si existe una versión "hermana" minificada del mismo código y actualizar ambas
4. Confirmar explícitamente al usuario qué se ha cambiado y por qué, ya que el histórico de esta app tiene varios ejemplos de fallos sutiles que costaron muchos intentos de depurar
